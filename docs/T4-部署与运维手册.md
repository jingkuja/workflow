# T4 部署与运维手册

适用版本：试用版 v1.0（T2 业务范围，T4 加固）

当前业务正常终态为 `WAITING_FOR_FILMING`。本版本不创建视频、剪辑或上架任务。

## 1. 上线前检查

1. 服务器为 Ubuntu x86_64，已安装 Docker Engine 与 Docker Compose。
2. 准备 `PUBLIC_BASE_URL`、老板/员工姓名、独立 Token、企业微信 `userid` 和群机器人
   Webhook。
3. 从 `.env.example` 生成 `.env`，替换全部开发密码和 Token，并执行
   `chmod 600 .env`。
4. 确认 `data/files` 可写、磁盘剩余高于 20%，443 转发目标为本机 8080。
5. 执行 `docker compose config --quiet`。两个 MCP 服务的环境中不得出现
   `POSTGRES_*`；`DATABASE_URL` 应为内存 SQLite 占位值，业务 PostgreSQL 仅由 API、
   Worker 和迁移服务持有。

关键配置：

| 配置 | 说明 |
| --- | --- |
| `PUBLIC_BASE_URL` | WorkBuddy 可访问的 HTTPS 根地址 |
| `INTERNAL_API_BASE_URL` | MCP 调用的容器内 API，默认 `http://workflow-api:8000` |
| `WEEKLY_TARGET_MIN/MAX` | 看板每周审核通过目标，默认 35/40 |
| `DISK_WARN_PERCENT` | 低于该剩余比例时就绪检查告警，默认 20 |
| `DISK_REJECT_PERCENT` | 低于该比例时拒绝新本地附件，默认 10 |
| `NOTIFICATION_SEND_ENABLED` | 完成真实群联调后才设为 `true` |

## 2. 首次部署

```bash
cp .env.example .env
chmod 600 .env
docker compose config --quiet
docker compose up --build -d --force-recreate
docker compose ps
```

检查：

```bash
curl --fail http://127.0.0.1:8080/health
docker compose exec -T workflow-api \
  python -c 'import urllib.request; print(urllib.request.urlopen("http://127.0.0.1:8000/health/ready").read().decode())'
```

然后分别使用老板和员工 Token 连接 `/mcp/boss`、`/mcp/employee`，确认工具白名单；
导入测试 Word，完成一次提交、驳回、重提和通过，并查询
`get_workflow_dashboard`。项目应停在 `WAITING_FOR_FILMING`。

## 3. 升级与回滚

固定执行顺序：

1. `scripts/backup_db.sh backups`，记录输出备份文件。
2. 拉取或切换到目标固定版本。
3. `docker compose build`。
4. `docker compose run --rm db-migrate`。
5. `docker compose up -d --force-recreate`。
6. 检查健康状态、MCP 工具列表和 T2 冒烟。

应用冒烟失败时，停止新版本应用容器，切回上一固定镜像或代码版本后重新启动。
不要自动降级数据库；若新迁移不兼容旧应用，使用对应版本的恢复说明和升级前备份。
附件目录及 `/files/{opaque_file_id}` 路由不能在回滚时改名或移动。

## 4. 备份与恢复演练

每日 PostgreSQL 逻辑备份，至少保留 7 份：

```bash
scripts/backup_db.sh backups
```

恢复演练只能使用隔离测试库：

```bash
scripts/restore_db_test.sh backups/备份文件.dump workflow_restore_test
```

脚本会重建指定测试库、恢复自定义格式备份，并检查 `alembic_version`。禁止把生产库名
作为第二个参数。恢复后还应抽查人员、项目、任务、附件元数据、提交、审核、通知和
审计记录数量。附件二进制是否备份由运维策略决定，但数据库恢复不能替代附件备份。

## 5. 日常检查

- `/health/ready`：数据库、附件目录、磁盘剩余比例和告警状态。
- `get_workflow_dashboard`：各阶段数量、演播稿积压、今日/本周审核通过量、35—40
  目标差额、优先任务、驳回、阻塞、失败任务/通知数量和人员负载。
- `list_operational_issues`：默认返回 `FAILED/DEAD` 后台任务、失败通知和 `OPEN`
  阻塞；可按 `issue_type`、`status` 分页过滤。
- `docker compose ps`：容器健康状态。
- `docker compose logs --since 30m SERVICE`：使用 `request_id` 关联 API、MCP 和
  Worker 日志；不要粘贴 Token、Webhook 或完整 `.env`。
- Docker 日志按每服务 20 MB、最多 5 份轮转。

## 6. 常见故障

| 现象/错误码 | 处理 |
| --- | --- |
| `UNAUTHENTICATED` | 检查 Bearer Token、人员是否在岗，修改配置后重启相关服务 |
| `FORBIDDEN` | 确认使用正确的老板/员工入口，员工不能访问他人任务 |
| 正确角色 Token 仍持续 `FORBIDDEN` | 检查 Nginx 是否加载 Docker DNS 动态解析配置；执行 `docker compose up -d --force-recreate reverse-proxy` |
| `IDEMPOTENCY_CONFLICT` | 不同业务内容改用新幂等键；相同请求继续使用原键 |
| `CONCURRENT_MODIFICATION` | 刷新详情和版本，确认最新状态后以新幂等键重试 |
| `INVALID_STATE_TRANSITION` | 刷新任务并只执行返回的 `next_actions` |
| `EXTERNAL_DEPENDENCY_FAILED` | 检查 `workflow-api` 健康和内部网络，再用相同幂等键重试 |
| 通知 `FAILED` | 等待 Worker 递增重试，检查网络、Webhook 和企业微信响应摘要 |
| 通知/任务 `DEAD` | 在 `list_operational_issues` 记录原因，修复依赖后由运维创建受控重试 |
| 下载 410 | 元数据存在但文件未就绪或已被清理；从备份恢复附件或要求重新提交 |
| 磁盘低于 20% | 盘点 `data/files` 和日志，按审计记录人工清理已确认可删除的附件 |
| 磁盘低于 10% | 系统会拒绝新附件；先扩容或清理，不要关闭保护阈值绕过 |

## 7. 人员与密钥变更

- 每人独立 Token，至少 16 字符；部署使用高强度随机值。
- Token 轮换：更新 `.env` 后重建 API、Worker 和两个 MCP；旧 Token 随即失效。
- 离职/停用：将员工 `active` 设为 `false`，先由老板改派未完成任务，再重建服务。
- 中文名是当前人员匹配键的一部分，不能直接在 `.env` 改名；应先用受控数据迁移更新
  `actor_profiles`，再同步配置，避免生成重复人员。
- `.env` 不提交 Git、不写进镜像、不通过聊天传输，权限保持 `600`。
